Developed by Anna Cao. Dataset built and populated by Anna Cao, Victoria Li, and Audrey Lau.

Roosevelt Networks is an interactive model of the actors that shape Roosevelt Island (agencies, organizations, institutions, buildings and people) and the relationships between them. This documentation explains how to use the app, how the model is constructed, and how to load your own dataset.

1. Overview

Roosevelt Networks treats the island as a network. Each actor (an agency, company, organization, institution, site or person with a stake in the island) is a node. Each documented relationship between two actors (funding, ownership, administration, collaboration and so on) is an edge. The model is built entirely in the browser from a shared spreadsheet. Every view in the app (Relationships, Map and Timeline) is a different arrangement of that same graph.

The pipeline, in order:

  1. Load the actor and adjacency tables from the published Google Sheet, falling back to a bundled snapshot.
  2. Join news-derived public interest and sentiment values onto actors.
  3. Build a typed multigraph: one node per actor and one edge per unique relationship.
  4. Derive edge widths and line styles from each relationship's parameters.
  5. Compute a force-directed layout from the relationship types that are switched on.
  6. Calculate centrality on whatever subset of the network is currently visible, and use it for halos, labels and the Centrality filter.

2. Data sources

Project spreadsheet

The primary dataset is a Google Sheet maintained by the project team, published to the web as CSV. The app requests each tab separately from the published endpoint:

https://docs.google.com/spreadsheets/d/e/<id>/pub?gid=<tab>&single=true&output=csv

A refresh timestamp parameter and cache: 'no-store' are added so a reload always returns the latest edits rather than a cached copy. Each request times out after 10 seconds. Actors are read from gid=1300872278 and adjacencies from gid=548852791. View the published dataset.

Local snapshot

A copy of each tab is bundled with the app under data/ (actors.csv and edges/adjacency.csv). If the sheet cannot be reached (a network error, an error response or a timeout), the app loads the snapshot instead. Actors that exist in the live sheet but not in the snapshot are tracked separately, so newly added actors can be identified. Relink data repeats the fetch on demand.

News metrics

Public interest (news hits) and public sentiment are read from a separate bundled table, actor database - actor_working - with news hits.csv, with columns actor, hits and sentiment. Rows are matched to actors by name, ignoring case and surrounding whitespace. Non-numeric values are treated as missing, as are negative hit counts. In the current snapshot, 188 actors have a hits value (0–100) and 213 have a sentiment value (about −0.69 to +0.77).

Geographic data

  • Building footprints: NYC Open Data / DoITT BUILDING dataset (5zhs-2jue), filtered to the island, one GeoJSON file per BIN.
  • Lot attributes: NYC DCP PLUTO 26v2 (64uk-42ks), joined by BBL.
  • Island boundary: OpenStreetMap relation 2389564.
  • Building–actor links: the buildings tab of the project spreadsheet (gid=1593670637).

Buildings

One row per building footprint, keyed by BIN (Building Identification Number). This tab is not read live. It is downloaded by a build script (npm run sync:buildings) that bakes the geometry into a single map overlay (see Map). Its columns are:

  • Identity and linkage: BIN, BBL (borough-block-lot), Name and Actor. Actor must match an actor value to anchor that actor on the map.
  • Site points: rows named point - "<name>" link a hand-placed point (for sites without a footprint, such as parks and ferry landings) to an actor.
  • Building attributes (DoITT): Address, Building Use, Construction Year, Roof Height.
  • Lot attributes (PLUTO): Land Use Code, Building Class, PLUTO Year Built, Floors, Residential Units, Total Units, Building Area (sq ft), Lot Area, commercial, residential, office, retail and other floor areas, Zoning District, Community District, Zip Code, Historic District, Landmark.

PLUTO describes tax lots, not buildings. The island's 68 footprints fall on only 17 lots, so lot-level values repeat across every building on the same lot. Treat them as lot totals, not per-building figures.

4. Network model

Graph construction

The network is stored as a graphology mixed multigraph (new Graph({ multi: true })). Multi means two actors can be joined by several edges of different types, e.g. a parent organisation that also funds its child. Mixed means directed and undirected edges coexist. While building the graph, the app:

  • Skips self-loops (an actor related to itself).
  • Keeps only the first occurrence of each type + source + target combination. For collaboration, the pair is order-independent, so A–B and B–A count as the same edge.
  • Skips any edge whose source or target is not in the actor table, and logs a warning naming the unmatched id.

Relationship types

Collaboration is the only undirected type. Every other type is directed from source to target and drawn with an arrow. Financial relationships are recorded recipient → sender (per the type name), but the arrow is drawn the other way so it follows the money from sender to recipient. Centrality calculations use the direction as recorded.

Parameter parsing

  • Money accepts an optional $, thousands separators and decimals (e.g. $1,250,000). Negative or non-numeric values are ignored.
  • Area accepts a number with an optional sq ft, sq feet or ft2 suffix. Values must be positive.
  • Closeness must be a positive whole number.
  • Edges with a missing or unparseable parameter keep the minimum width and are still part of the network.

Width scaling

Weighted widths are scaled linearly between 1 px and 5 px across the range of values in the whole dataset, so the smallest value in a type gets 1 px and the largest gets 5 px:

width = 1 + 4 × (v − vmin) / (vmax − vmin)

For Owner–Tenant, v is the square root of the parcel area, so line width tracks a parcel's side length rather than its area. This stops a few very large parcels from flattening all the others to the minimum. The legend reports the real minimum and maximum values behind each scale.

Parallel edges

When several edges join the same two actors, each is given a progressively larger curvature (starting at 0.05 and increasing in steps of 0.025) so they fan out instead of overlapping. The Connection curvature slider multiplies these offsets: 20% is the default curvature and 100% is five times as curved.

5. Centrality

Centrality measures how important an actor is to the structure of the network. Roosevelt Networks offers four measures. Degree is calculated directly, and the other three use graphology-metrics.

Which network is measured

Scores are never precomputed. Each time filters change, the app builds a temporary metric graph containing:

  • Actors that pass the Sector, Category, Scale and Time range filters, plus any pinned actors.
  • Edges whose relationship type is switched on (or which are pinned), and whose two ends are both included.

Every edge has a weight of 1, so parameters such as funding size do not influence centrality. Collaboration edges are undirected and all others keep their direction. As a result, an actor's centrality is relative to the slice of the network on screen. Turning off Financial relationships, for example, recalculates every score without funding links.

In the formulas below, N is the number of actors in the metric graph and d(u, v) is the number of steps on the shortest path from u to v.

Degree

The number of edges touching an actor: incoming plus outgoing plus undirected.

CD(v) = degin(v) + degout(v) + degundirected(v)

Because the graph is a multigraph, two edges of different types between the same pair count twice. Degree is reported as a raw count rather than normalised to 0–1, so the Centrality filter can be expressed in whole connections.

Closeness

How few steps it takes for the rest of the network to reach an actor. Computed with closenessCentrality(graph, { wassermanFaust: true }). A breadth-first search follows edges inbound (undirected edges count both ways), so distance is measured from other actors to v. If r is the number of other actors that can reach v:

CC(v) = (r / Σu d(u, v)) × (r / (N − 1))

The first term is ordinary closeness within the reachable part of the network. The second is the Wasserman–Faust correction, which scales the score by the share of the network that can reach v. Without it, an actor in a tiny isolated cluster would score as “close” as one at the heart of the main network. Actors that nobody can reach score 0.

Betweenness

How often an actor lies on the shortest paths between other actors, i.e. how much it acts as a broker or bridge. Computed with betweennessCentrality(graph, { getEdgeWeight: null }), which implements Brandes' algorithm on the unweighted graph:

CB(v) = [ Σs ≠ v ≠ t σst(v) / σst ] / ((N − 1)(N − 2))

Here σst is the number of shortest paths from s to t, and σst(v) is how many of them pass through v. Paths follow edge direction. The result is normalised by the number of ordered pairs of other actors, giving a value from 0 to 1.

Eigenvector

An actor is important if it is connected to other important actors. Computed with eigenvectorCentrality(graph, { getEdgeWeight: null, maxIterations: 500 }) by power iteration:

  1. Every actor starts with a score of 1/N.
  2. Each iteration, every actor passes its current score along its outgoing (and undirected) edges, and each actor keeps its own previous score as well: x ← x + ATx.
  3. Scores are divided by their Euclidean norm so they stay bounded.
  4. Iteration stops when the total change across all actors falls below N × 10−6, or after 500 iterations.

Because scores travel along edge direction, an actor ranks highly when well-ranked actors point to it. If the calculation fails to converge, which is rare, no eigenvector scores are shown and a warning is logged.

Where centrality is used

  • Halo: any of the four measures can set halo size (see Visual encoding).
  • Labels: actors are ranked by the selected measure. The top 10 get the largest labels. The rest are split at the median into medium and small labels, and smaller tiers only appear as you zoom in. The Labels slider hides labels by percentile rank, with tied scores sharing the same rank.
  • Centrality filter: steps through ranked degree values to hide less-connected actors. The filter currently applies to degree only; other measures leave every actor visible.
  • Details panel: “more central than X% of all other actors” is the share of other visible actors with a strictly lower score than the selected actor.

6. Layout

Relationships mode uses a force-directed layout, so actors with many shared relationships settle near each other. The steps are:

  1. Copy the graph, keeping only edges whose type is switched on.
  2. Place every actor on a circle (graphology-layout circular) to get a deterministic starting point.
  3. Run 150 iterations of ForceAtlas2 (graphology-layout-forceatlas2) with scalingRatio: 10. Connected actors attract, all actors repel, and gravity pulls everything toward the centre.

The Gravity slider (0–25) is converted to ForceAtlas2's gravity setting as 25 minus the slider value, so higher slider values apply weaker gravity and spread the layout out. The default of 20 gives gravity 5. The layout is recalculated and animated whenever relationship types are switched on or off, unless Freeze actor position is on.

Positions encode connectivity only. Distance on screen roughly reflects how many relationships separate two actors, but the axes have no meaning, and the same data can settle into a mirrored or rotated arrangement.

7. Visual encoding

Node size

Size encodes scale: micro actors are drawn at 0.5×, meso at 1.5× and macro at 4× a base radius. The Node size slider adjusts the base radius.

Node colour

  • Sector: one colour per type value, assigned from a fixed ten-colour palette in alphabetical order.
  • Category: one colour per topic, assigned the same way. An actor with several active topics is drawn as a pie with one slice per topic.
  • Public sentiment: a diverging scale from white (neutral) toward red, rgb(220, 28, 42), for negative sentiment and green, rgb(0, 154, 70), for positive. Intensity is (|s| / max|s|)0.7, where max|s| is the largest absolute sentiment in the dataset. The 0.7 exponent lifts weak values so mild sentiment stays visible. Actors without a value are grey.

Halo

The halo is a ring behind each node whose radius grows linearly from the node's own radius to 50 px. It is scaled by the actor's position between the minimum and maximum of the chosen metric among visible actors. The metric is Public interest (news hits) or one of the four centralities.

Edges

Each relationship type has a fixed colour (the financial colour darkens in light theme for contrast). Width and line style follow the parameter rules under Network model. When an actor or edge is selected, everything outside its neighbourhood is dimmed to 20% opacity.

8. Map

Building the overlay

Map geometry is prepared ahead of time by scripts/build-map-overlay.mjs:

  1. Optionally downloads the buildings tab as CSV (--sync), checking that the first header is BIN.
  2. Reads the island boundary and the bin-<BIN>.geojson footprint for every row with a BIN.
  3. Reprojects all coordinates from WGS84 longitude/latitude (EPSG:4326) to Web Mercator metres (EPSG:3857): x = Rλ, y = R ln tan(π/4 + φ/2), with R = 6,378,137 m. This keeps building proportions true instead of stretching them east–west.
  4. Writes everything into one SVG (map-overlay.svg), so the app makes one request instead of about 70. Each footprint path carries its BIN, name and linked actor as data attributes.
  5. Matches each point - "<name>" row to a point-<name>.svg file and writes the pairs to map-points.json.

Site points

Sites without a building footprint are drawn as individual SVGs (exported from Rhino), each containing the island outline in a group with id="boundary" and exactly one circle. The app applies any SVG transforms, measures the circle's position within the bounding box of the traced outline, and maps it to the same relative position within the real island's bounding box. Points therefore only need to be traced against the island outline, with no shared coordinate system.

Placing actors

  • An actor linked to one or more footprints is anchored at the average of those footprints' centroids.
  • An actor linked to a site point is anchored at that point, which takes priority over footprints.
  • The map is fitted, preserving its aspect ratio, into 60% of the network's extent and centred on it.
  • Anchored actors are fixed in place. ForceAtlas2 then runs again with the same settings, so unanchored actors settle around the anchors they are connected to. Gravity is recentred on the map so free actors gather around the island rather than the origin.
  • Leaving Map mode restores each anchored actor's previous position.

Unanchored actors' positions on the map are therefore relational, not geographic. They show who an actor is connected to, not where it is.

9. Timeline

Timeline mode (beta) arranges actors by their active years:

  • Each actor's bar runs from year_start to year_end, clipped to the visible range. A missing start or end extends the bar to that edge of the range.
  • Actors with no years at all are counted but not drawn.
  • Actors joined by Predecessor–Successor relationships are merged into a single row, ordered so each predecessor comes before its successor (a topological sort, with ties broken by start year then name).
  • Rows are nested under their parent through Parent–Child relationships. When a row has several parents, the closest earlier-starting parent is chosen.
  • Rows are ordered by start year, then alphabetically.

11. Limitations

  • Coverage: the network contains only relationships the team has documented. A missing edge means “not recorded”, not “no relationship”, and centrality inherits that bias.
  • Unweighted metrics: centrality ignores funding amounts, areas and collaboration closeness. Every relationship counts equally.
  • Relative scores: because centrality is recomputed on the visible network, scores are not comparable between different filter settings.
  • Mixed relationship semantics: direction means different things for different types (ownership, funding, succession), so directed measures such as closeness and eigenvector are most interpretable with a single relationship type, or a few related types, switched on.
  • News metrics are a proxy for public visibility and perception, matched by actor name. They are only available for actors with news coverage.
  • Lot-level data: PLUTO values describe tax lots, which can contain several buildings.
